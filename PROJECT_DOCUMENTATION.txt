1. PROJECT OVERVIEW & PROBLEM STATEMENT
====================================================================================================

Project Title:
  Public Health Biometric Face Mask and Compliance Verification Pipeline

Project Objective:
  To engineer an autonomous, real-time Computer Vision surveillance pipeline capable of detecting
  human faces in crowded video feeds, verifying biometric compliance against respiratory protective
  mandates, and accurately categorizing compliance into three operational states:
    1. Fully Compliant ('with_mask')
    2. Non-Compliant ('without_mask')
    3. Improperly Worn / Non-Compliant ('mask_weared_incorrect' - e.g., nose exposed, chin-dropped)

Real-World Relevance & Challenges:
  In pandemic response, clinical environments, airports, and crowded transit hubs, binary mask
  detectors (mask vs. no-mask) fail fundamentally because improper mask wear (such as exposing the
  nasal passages while covering the mouth) provides virtually zero respiratory filtration while giving
  a false sense of security. 
  Existing deep learning approaches suffer from three major roadblocks in real-world deployment:
    - Extreme Data Imbalance: Real-world benchmarks exhibit heavy skew (majority compliant faces,
      scant improper wear examples).
    - Latency Bottlenecks: Bulky end-to-end multi-task detectors (e.g., Faster R-CNN) cannot achieve
      real-time framerates (>25 FPS) on standard CPU hardware without costly dedicated GPUs.
    - Video Instability & Edge Artifacts: Frame-by-frame independent classification triggers severe
      bounding-box color flickering, while poor lighting and black/dark masks break traditional face
      detectors.

Hardware & Software Stack:
  - Language: Python 3.10 / 3.11
  - Core Deep Learning Framework: PyTorch >= 2.0.0, Torchvision >= 0.15.0
  - Computer Vision & Media: OpenCV (opencv-python >= 4.8.0)
  - Scientific Computing & Metrics: NumPy >= 1.24.0, Scikit-Learn >= 1.3.0
  - Visualization: Matplotlib >= 3.7.0
  - Execution Target: 100% open-source, runnable on standard laptop CPU (Intel Core i5/i7, AMD Ryzen)
    with zero proprietary cloud APIs or dedicated GPU dependencies.

2. SYSTEM ARCHITECTURE & DATA FLOW
====================================================================================================

Architectural Paradigm: Two-Stage Cascaded Decoupled Pipeline
Instead of training a monolithic single-stage detector (e.g., YOLO or SSD) to jointly predict face
location and 3-class mask compliance from full scenes, this project adopts a decoupled, two-stage
cascaded architecture:
  - Stage 1: Fast, scale-invariant face localization using an OpenCV Caffe SSD model.
  - Stage 2: High-resolution ROI classification using a transfer-learned MobileNetV2 network.

Clean ASCII System Flow Diagram:

  +---------------------------------------------------------------------------------+
  |                             LIVE INPUT FRAME                                    |
  |                   Webcam / RTSP Stream / Video File (HxWx3)                     |
  +---------------------------------------------------------------------------------+
                                           |
                                           v
  +---------------------------------------------------------------------------------+
  | STAGE 1: CONTRAST ENHANCEMENT & PREPROCESSING                                   |
  | - Convert Frame to LAB Color Space                                              |
  | - Apply CLAHE (clipLimit=2.0, tileGridSize=(8,8)) to L-Channel                  |
  | - Merge & Reconvert to BGR (Enhances dark masks, low-light contours)            |
  +---------------------------------------------------------------------------------+
                                           |
                                           v
  +---------------------------------------------------------------------------------+
  | STAGE 1: FACE DETECTION (OpenCV Caffe SSD - ResNet-10 Backbone)                 |
  | - cv2.dnn.blobFromImage(frame_clahe, 1.0, (300, 300), (104, 177, 123))         |
  | - Single Forward Pass -> Bounding Box Coordinates & Detection Confidence        |
  | - Confidence Threshold Guard: filter detections where confidence < 0.45         |
  +---------------------------------------------------------------------------------+
                                           |
                                           v
  +---------------------------------------------------------------------------------+
  | ROI EXTRACTION & ROBUST BOUNDARY CLAMPING                                       |
  | - Pass 1: Clamp normalized coords to [0.0, 1.0] -> Scale to frame (W, H)        |
  | - 10% Contextual Margin Padding: dX = 0.10 * W_box, dY = 0.10 * H_box           |
  | - Pass 2: Re-clamp padded box to [0, W] and [0, H]                              |
  | - Minimum Size Guard: Reject crops if (x2 - x1) < 50px or (y2 - y1) < 50px      |
  |   (Completely eliminates background objects, chairs, posters)                   |
  +---------------------------------------------------------------------------------+
                                           |

  +---------------------------------------------------------------------------------+
  | STAGE 2: DYNAMIC TENSOR BATCHING (PyTorch)                                      |
  | - For each valid face ROI: BGR -> RGB, Resize to 224x224, ImageNet Normalization|
  | - Stack K face crops into a single 4D Tensor: Batch Shape = [K, 3, 224, 224]    |
  | - Single Batched MobileNetV2 Forward Pass (Zero loop overhead)                  |
  | - Softmax Probability Vector Generation: [P(with), P(without), P(incorrect)]    |
  +---------------------------------------------------------------------------------+
                                           |
                                           v
  +---------------------------------------------------------------------------------+
  | TEMPORAL STABILIZATION: CENTROID TRACKER & 5-FRAME SMOOTHING                    |
  | - Match detected centroids to active face tracks (Euclidean Distance < 90px)    |
  | - Maintain rolling probability queue: deque(maxlen=5) per tracked identity      |
  | - Smoothed Probabilities = Mean of rolling 5-frame probability vectors          |
  +---------------------------------------------------------------------------------+
                                           |
                                           v
  +---------------------------------------------------------------------------------+
  | CALIBRATED DECISION LOGIC & HUD ANNOTATION                                      |
  | - If P_smooth(0) > 0.48 AND P_smooth(0) is highest -> Class 0 (with_mask: GREEN)|
  | - Else If P_smooth(2) >= 0.25 OR P_smooth(1) < 0.55 -> Class 2 (incorrect: AMBER)|
  | - Else -> Class 1 (without_mask: RED)                                           |
  | - Render Color BBoxes, Class Labels, Real-Time FPS, & Compliance Rate Badge     |
  +---------------------------------------------------------------------------------+

  +---------------------------------------------------------------------------------+
  |                           OUTPUT VIDEO STREAM                                   |
  |                   Real-Time Visual Display (30+ FPS CPU)                        |

Why Decouple Face Detection from Classification?
  1. Elimination of PyTorch Stage 1 Overhead: Running anchor generation, multi-scale feature
     pyramids, and non-maximum suppression (NMS) within PyTorch on CPU for full 1080p frames
     drops framerates to 6–10 FPS. OpenCV's C++ Caffe SSD backend executes in ~12ms on CPU.
  2. Independent Architectural Scaling: Detection models require spatial receptive fields to
     localize objects in large images; classification heads require deep semantic abstractions on
     focused crops. Decoupling allows using ImageNet-pretrained transfer learning on cropped faces.
  3. Superiority Over Haar Cascades: OpenCV Haar Cascades rely on hand-crafted edge/line features
     (integral images) that assume standard facial landmarks (visible nose bridge, mouth shadow).
     When a subject wears a mask, Haar Cascades suffer a catastrophic failure rate (>60% miss rate).
     The ResNet-10 Caffe SSD detects faces robustly under extreme occlusion, yaw angles, and masks.
  4. Cost Efficiency: Avoids expensive cloud compute; deployable on edge nodes, security NVRs, or
     low-cost classroom laptops.

3. DATASET & PREPROCESSING ENGINEERING (src/dataset.py)
====================================================================================================

Dataset Source:
  Kaggle Face Mask Detection Benchmark (andrewmvd/face-mask-detection).
  Format: 853 real-world multi-face images (.png) with PASCAL VOC XML annotations (.xml).

Dataset Distribution & Class Counts:
  The dataset contains a total of 3,833 annotated face bounding boxes.
  The distribution exhibits a severe class imbalance:
    - with_mask:                 3,060 faces (79.83%)
    - without_mask:                651 faces (16.98%)
    - mask_weared_incorrect:       122 faces ( 3.18%)
  The majority-to-minority ratio between 'with_mask' and 'mask_weared_incorrect' is 25.08:1.

Image-Level Stratified 80/20 Partitioning (Leakage Prevention):
  Standard random splitting at the crop level creates catastrophic data leakage: crops from the same
  image (sharing identical room lighting, camera sensor noise, and background context) would appear
  in both train and validation sets.
  To prevent this, partitioning is executed strictly at the IMAGE level:
    1. Every XML file is categorized by its rarest contained label:
       - Category 2: Contains at least one 'mask_weared_incorrect' face.
       - Category 1: Contains 'without_mask' faces (no incorrect).
       - Category 0: Contains solely 'with_mask' faces.
    2. Stratified split (80% train / 20% validation, random_state=42) is performed on unique images.
    3. Partition Statistics:
       - Total Images: Train = 682 images, Validation = 171 images.
       - Total Extracted Face Crops:
         * Train Split:      3,157 face crops
         * Validation Split:   676 face crops
       - Exact Per-Class Split:
         +-----------------------+-------------+------------+-------------+
         | Class Name            | Train Count | Val Count  | Total Crops |
         +-----------------------+-------------+------------+-------------+
         | with_mask (Class 0)   | 2,530       | 530        | 3,060       |
         | without_mask (Class 1)|   534       | 117        |   651       |
         | mask_incorrect (Cls 2)|    93       |  29        |   122       |
         +-----------------------+-------------+------------+-------------+
         | TOTAL                 | 3,157       | 676        | 3,833       |
         +-----------------------+-------------+------------+-------------+
       - Validation Guarantee: Validation set contains exactly 29 instances of the minority class
         (target was 20–25), providing a statistically reliable validation set for Macro F1 evaluation.

10% Context Padding Mathematics:
  Tight ground-truth bounding boxes clip off the mandible (jawline) and nasal apex. Without these
  surrounding anatomical context regions, a neural network cannot disambiguate between a properly
  seated surgical mask and a mask pulled down to expose the nostrils.
  Context padding formula implemented in src/dataset.py:
    Let bounding box dimensions be:
      W_box = x_max - x_min
      H_box = y_max - y_min
    Context offsets:
      delta_x = round(0.10 * W_box)
      delta_y = round(0.10 * H_box)
    Padded coordinates clamped to image dimensions (W_img, H_img):
      x1 = max(0, x_min - delta_x)
      y1 = max(0, y_min - delta_y)
      x2 = min(W_img, x_max + delta_x)
      y2 = min(H_img, y_max + delta_y)
    Validation check: Reject boxes where (x2 - x1) < 10 or (y2 - y1) < 10.

Smoothed Inverse Square-Root Class Weighting Formula:
  Standard inverse frequency weighting penalizes majority samples by the raw ratio:
    w_raw(c) = N_total / (C * N_c)
  For this dataset, w_raw would be:
    w_raw(with_mask) = 3157 / (3 * 2530) = 0.4159
    w_raw(incorrect) = 3157 / (3 * 93)   = 11.3154  -> Penalty ratio = 27.2:1!
  Applying a 27x loss multiplier causes severe over-sensitization: the classifier outputs massive
  false positives, flagging compliant masks as incorrect whenever a subject tilts their head.

  Solution: Smoothed Inverse Square-Root Weighting:
    w_smooth(c) = sqrt( N_total / (C * N_c) )
  Normalized so that sum(w_smooth) == C (where C = 3):
    - with_mask (Class 0):                 0.3575
    - without_mask (Class 1):              0.7781
    - mask_weared_incorrect (Class 2):     1.8645
  Smoothed Weight Ratio:
    w(Class 2) / w(Class 0) = 1.8645 / 0.3575 = 5.22:1
  This 5.22:1 ratio provides strong gradient signal to learn improper wear features while keeping
  precision high and preventing false alarms during live inference.

Data Augmentation & Normalization Pipeline:
  - Training Pipeline:
    1. Crop ROI with 10% context padding
    2. Resize to (224, 224)
    3. Random Horizontal Flip (p=0.5)
    4. Color Jitter: brightness=0.2, contrast=0.2, saturation=0.2 (simulates diverse camera sensors)
    5. ToTensor() -> Scales pixel intensities to [0.0, 1.0]
    6. Normalize with ImageNet standard statistics:
       mean = [0.485, 0.456, 0.406], std = [0.229, 0.224, 0.225]
  - Validation Pipeline:
    Resize(224, 224) -> ToTensor() -> Normalize(mean, std)

4. MODEL ARCHITECTURE & TRAINING STRATEGY (src/model.py & src/train.py)
====================================================================================================

Backbone Network: MobileNetV2
  MobileNetV2 uses inverted residual blocks with linear bottlenecks. It reduces computational
  complexity (FLOPs) and memory footprint while retaining representational capacity via depthwise
  separable convolutions.
  - Input Shape: [Batch_Size, 3, 224, 224]
  - Pretrained Weights: MobileNet_V2_Weights.DEFAULT (ImageNet-1k)

Classification Head Engineering (Fixing the Double-Dropout Flaw):
  Torchvision's default mobilenet_v2 definition has:
    model.classifier = nn.Sequential(
        nn.Dropout(p=0.2),
        nn.Linear(1280, 1000)
    )
  A common student flaw is replacing model.classifier[1] with another Dropout + Linear layer,
  resulting in back-to-back dropouts (Dropout(0.2) -> Dropout(0.3)), which drops ~44% of activations
  and impairs feature transfer.
  In src/model.py, the entire classifier is cleanly replaced:
    model.classifier = nn.Sequential(
        nn.Dropout(p=0.2),
        nn.Linear(model.last_channel, 3)  # 1280 -> 3
    )

Parameter Breakdown:
  +--------------------------------+-----------------+------------------+-----------------+
  | Training Phase                 | Total Params    | Trainable Params | Frozen Params   |
  +--------------------------------+-----------------+------------------+-----------------+
  | Stage 1 (Epochs 1–5: Head Only)| 2,227,715       | 3,843 (0.17%)    | 2,223,872       |
  | Stage 2 (Epochs 6–20: Top-4)   | 2,227,715       | 1,529,923 (68.7%)|   697,792       |
  +--------------------------------+-----------------+------------------+-----------------+

Two-Stage Progressive Fine-Tuning Schedule:
  - Stage 1 (Warmup: Epochs 1 to 5):
    * Strategy: Backbone features completely frozen (model.features.requires_grad = False).
    * Target: Adapt randomly initialized 1280 -> 3 classification head without corrupting pretrained
      low-level and mid-level feature representations.
    * Optimizer: Adam(model.classifier.parameters(), lr=1e-3, weight_decay=1e-4)
    * Scheduler: CosineAnnealingLR(optimizer, T_max=5, eta_min=1e-5)
  - Stage 2 (Fine-Tuning: Epochs 6 to 20):
    * Strategy: At Epoch 6, unfreeze the top 4 inverted residual blocks (model.features[-4:]).
    * Technical Rationale: ImageNet features are general (dogs, vehicles, textures). Distinguishing
      a mask worn under the nose vs. over the nose requires the network to adapt high-level facial
      geometry without forgetting basic edge/shape primitives.
    * Fresh Differential-LR Adam Optimizer instantiated at Epoch 6:
        optimizer = torch.optim.Adam([
            {'params': model.features[-4:].parameters(), 'lr': 1e-4}, # Low LR for backbone
            {'params': model.classifier.parameters(),    'lr': 1e-3}  # Higher LR for head
        ], weight_decay=1e-4)
    * Scheduler: CosineAnnealingLR(optimizer, T_max=15, eta_min=1e-6)

Training Execution Hyperparameters:
  - Batch Size: 32 face crops
  - Loss Function: nn.CrossEntropyLoss(weight=smoothed_class_weights)
  - Device: Standard Laptop CPU
  - Total Epochs: 20 epochs
  - Checkpoint Criteria: Lowest validation loss (saved to models/mask_classifier.pth)
  - Optimal Checkpoint: Achieved at Epoch 14 (Validation Loss = 0.2506, Macro F1 = 0.8360)

6. REAL-TIME SURVEILLANCE & EDGE OPTIMIZATION (src/inference.py)
====================================================================================================

Stage 1 Face Detection Engine:
  - Architecture: ResNet-10 based Single Shot MultiBox Detector (SSD) loaded via OpenCV DNN module
    (cv2.dnn.readNetFromCaffe).
  - Model Files: models/face_detector/deploy.prototxt and res10_300x300_ssd_iter_140000.caffemodel.
  - Input Blob: cv2.dnn.blobFromImage(frame, 1.0, (300, 300), (104.0, 177.0, 123.0), swapRB=False).
  - Confidence Threshold: Set to 0.45 (balances sensitivity and noise rejection).

CLAHE Contrast Enhancement (LAB Color Space):
  - Problem: Black cloth masks and low-light surveillance feeds blend into facial shadows, causing
    SSD face detectors to fail completely.
  - Implementation: Convert RGB frame to LAB space, apply Contrast Limited Adaptive Histogram
    Equalization (CLAHE: clipLimit=2.0, tileGridSize=(8, 8)) to the L (luminance) channel, and
    reconvert to BGR before passing to the SSD detector.
  - Result: Dark masks and shaded facial features achieve sharp edge boundaries for reliable face
    bounding box extraction.

Edge Guarding & Crash-Proofing:
  - Two-Pass Clamping: Raw SSD coordinates frequently output values < 0.0 or > 1.0 near frame edges.
    Coordinates are clamped to [0, W] and [0, H] before padding, padded by 10%, and clamped again.
  - 50px Minimum Size Guard: Rejects crops with width < 50px or height < 50px. This completely
    filters out false background triggers (e.g. textured chair backs, circular logos, distant mugs)
    without missing foreground faces.
  - Zero Empty-Slice Crashes: Guarantees cv2.resize() never encounters an empty slice (!ssize.empty()).

Dynamic PyTorch Tensor Batching:
  - If a frame contains K faces, naïve implementations run K sequential forward passes:
      for face in faces: output = model(face)  # High latency overhead
  - Our Implementation: Preprocesses all K face crops in NumPy, stacks them into a single 4D PyTorch
    tensor [K, 3, 224, 224], and executes ONE single forward pass per frame.
  - Benchmark Result: Sustains 30+ FPS even when multiple faces occupy the camera field of view.

Temporal Stabilization: Centroid Tracker & 5-Frame Rolling Window:
  - Problem: Single-frame predictions jitter between Green and Amber as head movement changes lighting.
  - Solution: A Euclidean CentroidTracker matches face bounding boxes across frames (distance < 90px).
  - Rolling Deque: Each active face maintains a deque(maxlen=5) storing the last 5 probability vectors.
  - Smoothed Probabilities: P_smooth = mean(deque, axis=0). Bounding box colors remain rock-solid.
  - Disappeared threshold of 15 frames automatically unregisters tracks when subjects exit the frame.

Calibrated Classification Decision Logic:
  To eliminate Green/Amber flickering on masks worn with eyeglasses, decision boundaries were
  calibrated based on empirical validation distributions:
    ```python
    if smoothed_probs[0] > 0.48 and smoothed_probs[0] >= smoothed_probs[1] and smoothed_probs[0] >= smoothed_probs[2]:
        pred_cls = 0  # Compliant (with_mask: GREEN)
    elif smoothed_probs[2] >= 0.25 or smoothed_probs[1] < 0.55:
        pred_cls = 2  # Incorrect Wear (mask_weared_incorrect: AMBER)
    else:
        pred_cls = 1  # Non-Compliant (without_mask: RED)
    ```
  - Eyeglass Stability: Glasses frames on the nasal bridge lower 'with_mask' probability to 50–70%.
    Because 0.48 is the dominance barrier, properly masked subjects with glasses stay steadily Green.
  - Sensitive Amber Trigger: Nose-exposed masks split probability between mask and bare skin. If bare-face
    confidence cannot exceed 55% or class 2 probability crosses 25%, Amber is triggered reliably.

Clean Exit & Window Management:
  - Listens for 'q', Esc (ASCII 27), and captures snapshots with 's'.
  - Checks cv2.getWindowProperty(window_name, cv2.WND_PROP_VISIBLE) < 1, allowing users to close the
    feed immediately by clicking the window's 'X' button without terminal lockups.

SLIDE 5: Loss Engineering & Imbalance Mitigation

Title: Smoothed Inverse Square-Root Loss Weighting

Slide Content (Bullet Points):
  * The 25:1 Imbalance Challenge: with_mask (2,530 train) heavily outnumbers incorrect (93 train).
  * Flaw of Raw Inverse Frequency:
    - Raw formula: w = N / (C * N_c) assigns a 27.2:1 penalty ratio (weight ~11.3 vs ~0.42).
    - Failure Mode: Causes massive false alarms, flagging compliant users as incorrect on live camera.
  * Our Solution: Smoothed Inverse Square-Root Weighting:
    - Formula: w_smooth = sqrt( N / (C * N_c) ), normalized so sum(w) = 3.
    - Resulting Weights: with_mask = 0.3575, without_mask = 0.7781, incorrect = 1.8645.
    - Softened Penalty Ratio: 5.22:1 (balances minority gradient signal without destabilizing precision).

Speaker Notes:
  "Because the minority class accounts for only 3.2% of the dataset, standard cross-entropy loss
   would ignore improper wear entirely. However, raw inverse frequency weighting introduces an
   over-correction penalty of 27:1, which causes the live demo to falsely flag compliant faces as
   incorrect. We engineered a smoothed inverse square-root weighting formula that tempers the penalty
   ratio to 5.22:1. This gives the minority class sufficient gradient impact during backpropagation
   while maintaining high precision during live surveillance."

SLIDE 6: Deep Learning Model Architecture
----------------------------------------------------------------------------------------------------
Title: MobileNetV2 Transfer Learning & Head Redesign

Slide Content (Bullet Points):
  * Backbone: MobileNetV2 with inverted residual bottlenecks and depthwise separable convolutions.
  * Input Resolution: 224 x 224 x 3 normalized with ImageNet mean and variance.
  * Fixing Double-Dropout:
    - Default torchvision model has Dropout(0.2) in classifier[0].
    - Nesting a custom head inside classifier[1] created an accidental Dropout(0.2) -> Dropout(0.3)
      stack, dropping ~44% of features.
    - Redesign: Replaced entire classifier with nn.Sequential(nn.Dropout(p=0.2), nn.Linear(1280, 3)).
  * Low Parameter Footprint: Only 2.23M total parameters—ideal for real-time edge execution.

Speaker Notes:
  "For our classification backbone, we selected MobileNetV2 due to its inverted residual structure
   and lightweight parameter count of 2.23 million parameters. During implementation, we eliminated
   a subtle bug present in many PyTorch implementations: torchvision's MobileNetV2 already includes
   a 0.2 dropout layer. Nesting another dropout layer in the head results in a cascading 44% feature
   dropout. We replaced the entire classifier attribute cleanly with a single Dropout(0.2) followed
   by a Linear layer mapping 1,280 bottleneck features directly to our three compliance classes."

SLIDE 7: Two-Stage Progressive Fine-Tuning
----------------------------------------------------------------------------------------------------
Title: Progressive Unfreezing & Differential Learning Rates

Slide Content (Bullet Points):
  * Phase 1 (Epochs 1–5: Linear Probing):
    - Backbone features frozen (2,223,872 params frozen; only 3,843 head params trainable).
    - Trains new classifier head at lr = 1e-3 with Adam and Cosine Annealing.
    - Prevents large random head gradients from wiping out pretrained ImageNet feature extractors.
  * Phase 2 (Epochs 6–20: Top-4 Block Adaptation):
    - Unfreezes top 4 inverted residual blocks (model.features[-4:]), increasing trainable params to 1.53M.
    - Fresh Differential-LR Adam Optimizer instantiated at Epoch 6:
      * Backbone blocks: lr = 1e-4 (gentle adaptation for high-level facial geometry).
      * Classifier head: lr = 1e-3 (rapid convergence).
  * Optimal Convergence: Best checkpoint achieved at Epoch 14 (Val Loss = 0.2506).

Speaker Notes:
  "Training a transfer-learning model on an imbalanced dataset requires a two-stage strategy. In
   Epochs 1 through 5, we freeze the entire backbone and train only the 3,843 parameters of the
   linear head at a learning rate of 1e-3. This warms up the classifier. At Epoch 6, we unfreeze the
   top four inverted residual blocks, unlocking 1.53 million parameters, and instantiate a fresh
   differential-LR Adam optimizer: 1e-4 for the backbone and 1e-3 for the head. This allows the network
   to adapt to subtle facial geometry—such as an exposed nose bridge—achieving optimal validation

8. VIVA DEFENSE EXAMINATION Q&A BANK (TOP 10 TECHNICAL QUESTIONS)
====================================================================================================

QUESTION 1:
Why did you choose a decoupled two-stage architecture (Caffe SSD + MobileNetV2) instead of training
an end-to-end object detector like YOLOv8 or Faster R-CNN directly on the full images?

ANSWER:
"Decoupling the pipeline provides three critical advantages. First, computational efficiency on CPU:
OpenCV's C++ Caffe SSD backend localizes faces in 12ms, whereas running anchor-based region proposal
networks or multi-scale path aggregation networks in PyTorch on full 1080p frames consumes 80–120ms
on CPU, making real-time 30 FPS impossible without a GPU. Second, architectural specialization: face
detection requires translation invariance and scale robustness across wide scenes, while compliance
classification requires deep, high-resolution semantic discrimination on cropped facial features.
Third, modularity: decoupling allows us to independently apply CLAHE contrast enhancement for face
discovery, dynamically batch face crops into PyTorch, apply temporal smoothing per face track, and
retrain the classification head without modifying the face detector."

----------------------------------------------------------------------------------------------------

QUESTION 2:
Why not use OpenCV Haar Feature-based Cascades for Stage 1, which are even faster than Caffe SSD?

ANSWER:
"Haar Cascades rely on hand-crafted contrast features (integral images) that expect predefined facial
geometry, specifically the shadow of the nose bridge, mouth line, and eye sockets. When a subject wears
a mask, over 50% of these geometric landmarks are completely occluded, causing Haar Cascades to suffer
a catastrophic miss rate exceeding 60%. Furthermore, Haar Cascades are notoriously fragile under out-of-plane
rotations and varying illumination. In contrast, OpenCV's ResNet-10 Caffe SSD is a deep convolutional
detector that learns hierarchical spatial representations, allowing it to detect faces under extreme
occlusions, yaw angles, and varied lighting conditions."

----------------------------------------------------------------------------------------------------

QUESTION 3:
What is data leakage in the context of object cropping, and how did your dataset pipeline prevent it?

ANSWER:
"The Kaggle Face Mask Detection dataset contains 853 images containing multiple faces in the same scene.
If you crop all 3,833 faces first and then perform a standard random 80/20 train/test split, crops from
the exact same image will end up in both the training set and the validation set. Because faces in the
same image share identical room illumination, background clutter, camera sensor artifacts, and often
the same individuals across continuous frames, the model memorizes these environmental shortcuts,
yielding artificially inflated validation scores that collapse in real-world deployment. In src/dataset.py,
we prevented this by executing an image-level stratified split: the 853 image files themselves were
partitioned 80/20 based on minority class presence before any cropping occurred. All crops from a given
image strictly remain in either the train set (682 images, 3,157 crops) or the validation set (171 images,
676 crops)."

----------------------------------------------------------------------------------------------------

QUESTION 4:
Why was 10% context padding added to the bounding box crops, and what happens if you omit it?

ANSWER:
"Ground-truth annotation bounding boxes in detection datasets are drawn tightly around the face. If you
crop tightly along these coordinates, the lower margin clips off the mandible and chin, while the upper
margin clips off the nasal bridge. Distinguishing between 'with_mask' and 'mask_weared_incorrect' requires
observing whether the mask covers the nasal columella or is pulled down to rest on the chin. Without the
10% margin, the classifier cannot view the surrounding anatomical landmarks, leading to high false
negative rates on improperly worn masks. The 10% padding formula expands the box by 10% of its width
and height in all four directions, followed by boundary clamping to [0, W] and [0, H] to prevent negative
indexing."

----------------------------------------------------------------------------------------------------

QUESTION 5:
Explain the mathematics of your class weighting strategy. Why did you use smoothed inverse square-root
weights instead of standard inverse frequency weighting?

ANSWER:
"Our training set contains 2,530 'with_mask' faces, 534 'without_mask' faces, and only 93 'mask_weared_incorrect'
faces. Standard inverse frequency weighting calculates w_c = N_total / (C * N_c), which yields a weight
of 0.416 for with_mask and 11.315 for incorrect wear—an extreme penalty ratio of 27.2:1. When deployed
on a live webcam, this 27x multiplier severely over-sensitizes the network: even minor shadows or slight
head rotations cause the model to output a high minority loss gradient, resulting in rampant false
positives where compliant masks are classified as incorrect. We implemented smoothed inverse square-root
weighting: w_c = sqrt( N_total / (C * N_c) ), normalized to sum to 3. This softened the weight ratio
from 27.2:1 down to 5.22:1 (with_mask = 0.3575, incorrect = 1.8645). This provided sufficient gradient
emphasis to achieve 65.52% recall on the minority class without triggering false alarms."

----------------------------------------------------------------------------------------------------

QUESTION 6:
What was the double-dropout bug in the initial MobileNetV2 architecture, and how was it corrected?

ANSWER:
"In torchvision's mobilenet_v2 definition, the classifier block is defined as:
  nn.Sequential(nn.Dropout(p=0.2), nn.Linear(1280, 1000)).
A frequent bug in transfer learning is replacing model.classifier[1] with another sequential layer containing
its own dropout, such as nn.Sequential(nn.Dropout(p=0.3), nn.Linear(1280, 3)). This creates two consecutive
dropout layers: Dropout(0.2) immediately followed by Dropout(0.3). Mathematically, the probability of an
activation surviving is (1 - 0.2) * (1 - 0.3) = 0.56, meaning 44% of features are randomly dropped right
before the linear projection. This excessively degrades feature transfer on small datasets. In src/model.py,
we corrected this by cleanly reassigning model.classifier to a single nn.Sequential(nn.Dropout(p=0.2),
nn.Linear(1280, 3)), preserving optimal feature flow."

----------------------------------------------------------------------------------------------------

QUESTION 7:
Why did you implement a two-stage progressive fine-tuning schedule with differential learning rates
instead of training the entire network end-to-end from Epoch 1?

ANSWER:
"When transfer learning from ImageNet, the feature extractor backbone contains highly optimized convolutional
filters, while the newly replaced 1280 -> 3 classification head contains completely random weights. If you
train the entire network end-to-end from Epoch 1 with a uniform learning rate, the massive loss gradients
computed from the random head backpropagate into the backbone, causing 'catastrophic forgetting'—destroying
the pretrained feature filters. In our training loop (src/train.py):
  - Stage 1 (Epochs 1–5): We froze all 2.22M backbone parameters and trained only the 3,843 parameters of
    the head at lr = 1e-3, stabilizing head weights.
  - Stage 2 (Epochs 6–20): We unfroze only the top 4 inverted residual blocks (model.features[-4:]) and
    instantiated a fresh differential Adam optimizer: lr = 1e-4 for backbone blocks (gentle refinement
    of high-level facial geometry) and lr = 1e-3 for the head. This yielded our best validation loss of
    0.2506 at Epoch 14."

----------------------------------------------------------------------------------------------------

QUESTION 8:
Why is Macro Average F1-score more important than Overall Accuracy when evaluating this model?

ANSWER:
"Accuracy simply measures the percentage of correct predictions over the entire dataset: (TP + TN) / Total.
Because our validation set has 530 'with_mask' crops out of 676 total samples (78.4%), a trivial, naive
model that outputs 'with_mask' 100% of the time would achieve 78.4% accuracy while being completely useless
for public health enforcement. Macro Average F1 calculates the unweighted harmonic mean of precision and
recall independently for each of the three classes and then averages them: (F1_with + F1_without + F1_incorrect) / 3.
Because every class contributes equally (33.3%) to Macro F1 regardless of its sample size, an algorithm
cannot achieve a high Macro F1 without performing well on the minority class. Our model achieved an overall
accuracy of 94.67% and a Macro F1 of 0.8360, proving genuine multi-class competence."

----------------------------------------------------------------------------------------------------

QUESTION 9:
How does your inference pipeline maintain 30+ FPS on a standard laptop CPU when multiple people appear
in the webcam frame?

ANSWER:
"The primary latency bottleneck in multi-face surveillance is sequential invocation of deep neural networks.
If a frame contains 5 detected faces, calling model(face) in a Python 'for' loop invokes PyTorch kernel
launches, memory copies, and thread synchronization 5 separate times, causing framerate drops to 10–15 FPS.
In src/inference.py, we implemented Dynamic PyTorch Tensor Batching:
  1. All K detected face crops in the frame are preprocessed in parallel into standardized [3, 224, 224] arrays.
  2. The crops are stacked along the batch dimension into a single 4D PyTorch tensor: [K, 3, 224, 224].
  3. A single forward pass is executed: with torch.no_grad(): logits = model(batch_tensor).
Modern CPU vector extensions (AVX-512 / AVX2) parallelize matrix multiplications across the batch dimension
far more efficiently than sequential single-sample passes, allowing our pipeline to sustain 30+ FPS even
with 5–8 concurrent faces."

----------------------------------------------------------------------------------------------------

QUESTION 10:
How did you solve the live webcam bounding box color flickering and eyeglass misclassifications?

ANSWER:
"Flickering occurs because frame-by-frame classifications are independent; subtle head motion or lighting
fluctuations cause softmax probabilities to jump across decision boundaries between consecutive frames.
We implemented three complementary solutions:
  1. CentroidTracker with Rolling Temporal Smoothing: Detected face centroids are tracked across frames
     (distance < 90px). Each track maintains a deque(maxlen=5) storing the probability vectors of the
     last 5 frames. The classification decision is made on the rolling mean probability vector, eliminating
     single-frame jitter.
  2. CLAHE Preprocessing on LAB L-Channel: Applying CLAHE to the luminance channel before SSD detection
     enhances facial boundaries and dark mask contours under poor lighting.
  3. Calibrated Decision Thresholding: Subjects wearing eyeglasses often exhibit a slight reduction in
     'with_mask' probability (dropping to 50–70%) due to glasses frames occluding the nasal bridge.
     Our decision logic requires smoothed_probs[0] > 0.48 and dominant to lock in Green ('with_mask').
     Amber ('mask_weared_incorrect') is only triggered if class 2 probability crosses 0.25 or bare skin
     confidence fails to reach 0.55. This guarantees that compliant mask wearers with glasses remain
     steadily Green."
